# 单 / 多 Agent 真实模型对照

补齐高德 / Tavily 后，已用相同问题集复测，见 [新配置对照报告](AGENT_COMPARISON_2026-10-10_WITH_KEYS.md)。本文件及原始 JSON 保留为未配置这两个 Key 时的基线。

2026-10-10，使用项目当前实现进行 15 组对照：12 个不同问题，加 3 个复杂问题各重复一次，共 30 份回答。全部完成，无图执行异常或工具回调异常；临时测试账号已删除。完整问题、历史、记忆背景、回答、工具输入输出及领域中间回答见 [JSON 原始记录](AGENT_COMPARISON_2026-10-10.json)。

## 结论

本次多 Agent 有时会把单 Agent 已获取、但未写进最终答案的细节补充出来。例如，天气 + 穿搭 + 地铁问题的两次对照中，多 Agent 都保留了当天完整的 `21.6~31.2°C` 气温范围，单 Agent 只报告实时气温或最高温。行程问题中，多 Agent 额外报告了后天天气，并调用了额外的天气工具。

这些结果体现的是调用和信息保留的差别，**没有证明多 Agent 能访问单 Agent 无法访问的信息**。实测单 Agent 工具集合与多 Agent 各领域工具的并集完全相同，都是 10 个工具；同一组输入的用户身份、近期历史、卡片与历史 RAG 背景相同。私人攻略、个人行程、历史暗号和省略式追问，两种模式均能处理。

多 Agent 并未稳定提高答案质量。本批有无关搜索、领域之间相互矛盾的“查不到”、今天与明天天气混淆，以及没有工具依据的具体地铁换乘说明。单 Agent 也有未经工具验证的路线补充。不能把更长的答案或更多工具调用直接算作能力提升。

## 测试方法与边界

- 对话模型：真实 DeepSeek `deepseek-chat`，温度 0.3；两种模式共用模型配置。
- 外部数据：真实 Open-Meteo 天气、智谱 `embedding-3` 1024 维、百炼 `gte-rerank-v2`，配合真实 PostgreSQL 的 BM25 + pgvector + RRF 检索。
- 临时用户有明天 `09:20` 广州博物馆的合成行程；上传一份合成书店攻略，包含 `13:40`、鹭江地铁站 A 出口、`青禾714`。
- 用原话证据写入“常住海珠区、喜欢微辣”卡片，另将“蓝鲸7429”活动暗号写入历史并索引。每组先生成一份真实记忆背景，再原样交给两种模式。本次比较背景的使用，不重复测试自动卡片抽取；抽取验证见 [双层记忆验收](MEMORY_LIVE_TEST_2026-10-10.md)。
- 追问用例给两种模式相同的两条历史，明确先前目的地为广州塔，再问“那我今天去那里怎么穿？”。本次不将生成的答案写回聊天历史，避免先运行的模式影响后运行的模式。
- 每组交替先运行 single / multi；组内顺序执行，两种图与工具事先加载。直接调用实际 LangGraph 图，而非 HTTP/SSE 入口；耗时不包含共享记忆准备、消息保存或流式传输。网络延迟、实时天气更新和模型随机性仍会影响结果。
- 未配置高德 Key，路线工具走项目内置估算。`28 分钟 / 9.1 元` 等是回退算法输出，不能当作实时导航或真实出租车价格。工具文本没有具体换乘站；模型自行补充的线路不计为验证过的新信息。
- 未配置 Tavily Key，联网搜索尝试了 DuckDuckGo 回退，本次调用未得到结果。公共知识库的景点描述也不代表实时营业情况；本实验不评价真实景点服务或实际旅行安排。

## 具体证据

**信息保留的优势：** `three_domains` 两次中，两边均调用 `get_weather`、`recommend_outfit`、`plan_travel_route`。原始工具结果含当天最低 / 最高温与三种路线，多最终答案保留完整温度范围和更多路线字段；单最终答案较精简。单已拿到这些内容，只是在这次生成时没有全部展示。`itinerary` 多另外调用 `get_weather`、`get_forecast`，报告后天 `23.4~33.5°C`；单仅调用行程提醒。单拥有同样的预报工具，因此也不能解释为单无法获取。

**并行隔离造成的负面例子：** `private_weather_outfit` 的 itinerary 节点读出集合时间、集合点和口令，weather 节点查到实时天气；但 knowledge 节点称攻略与天气查不到，outfit 节点让用户重新发送攻略。最终汇总已给出答案，却仍留下“确认上传是否成功”的提示。这是各节点只看到自己的工具结果、汇总又没有充分消解冲突的表现。单 Agent 的同一消息列表连续包含私人资料、天气和穿搭结果，两次回答均完成核心任务。

**时间条件没有贯穿工具：** `itinerary_route_outfit / 2` 的 weather 节点给出明天“晴、21.6~32.6°C”；穿搭工具只接受城市 / 场景等参数，使用今天“阴、21.6~31.2°C”。汇总将两者说成预报来源冲突。单 Agent 也使用同一穿搭工具，但最终按明天预报组织答案。这次表现差异并不保证下一次同样发生；工具缺少目标日期是两种模式共享的能力边界。

**未验证信息不能算优势：** `three_domains / 1` 的多回答给出具体地铁换乘与约 40 分钟，但路线工具只给估算 57 分钟、没有换乘站；重复时又明确说查不到具体线路。`route / 1` 单回答也自行补充了出租车价格。当前不存在校验这些新增内容的共同步骤。

## 复现与代码变动

backend 目录执行 `python -m app.scripts.compare_agents_live`，需要项目数据库和已配置的模型 Key，会产生真实 API 费用，写入当天的 JSON 报告。重复执行会覆盖同日期报告，需保留原结果时先复制文件。

修正旧对比脚本将多 Agent 初始 `domains` 设为 `[]` 的问题：当前 supervisor 把非 None 值视为已路由，旧脚本实际跳过领域 Agent、走通用回答。现在使用 `None` 触发真正路由，并记录真实工具输入输出、共享背景与用户上下文。新增两个回归用例，以完整图 + 模型替身验证单 / 多入口都会实际调用工具、准确统计调用次数及隔离用户上下文。未修改生产 Agent 编排或本地 `.env`。
