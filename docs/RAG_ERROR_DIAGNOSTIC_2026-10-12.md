# RAG 检索与回答错误诊断（2026-10-12）

## 结论

复现了“检索得到完整证据，但最终回答错误”的情况。根因位于工具上下文组装：`search_my_plans` 把每个检索块截到前 200 字，而分块器允许最多 300 字。第 200 字之后的有效事实被丢弃，单/多 Agent 都将“工具摘要未提供”误说成“用户资料没有”。两次独立测试、四份 Agent 回答均复现。其中两份多 Agent 回答的核验（每次测试各一份）均返回 `passed`，因为验证节点读取的是相同的截断工具结果。

本次有答案的 7 个初始问题均在 Top-5 找到正确文档；新旧通知案例的新通知位于第 2 名，其余目标第 1 名。未复现这些案例的核心召回遗漏。完整检索结果直接交给真实 DeepSeek 时，8 个初始案例及 1 个复测案例均符合人工设定的答案或拒答要求；没有在这批完整上下文回答中复现纯生成层的事实幻觉。这是有限样本，不能推断所有问题均正确。

另观察到无关问题仍返回 5 条低相关候选、外部 Embedding/rerank 临时失败触发降级。应将“召回非空”“接口 200”“模型核验 passed”与答案正确分开评估。

## 方法与范围

- 真实开发 PostgreSQL、智谱 `embedding-3`（1024 维）、百炼 `gte-rerank-v2` 和 DeepSeek `deepseek-chat`。
- 原有真实脚本通过 FastAPI ASGI 调用公共/私人检索接口，另验证历史检索及原生 Retrieval Chain；7 个基线案例通过，没有模型回退告警。
- 新诊断脚本创建两个临时合成用户，上传 8 篇本人资料和 1 篇他人资料，测试 8 个问题；其中 7 个问题分别运行完整单/多 Agent 图，共 14 份回答。再独立重建同一合成语料复测截断案例，增加 2 份 Agent 回答。
- 同时记录源文档、完整检索块、实际 Agent 发起的检索及返回块、工具输出、最终回答和多 Agent 核验。图直接执行，不通过聊天 HTTP 入口，不写聊天历史、不启用请求级记忆/检查点；HTTP 基线由已有脚本覆盖。
- 文档指令案例明确标记恶意内容，且问题提醒忽略文档指令；只能说明此样例未被注入，不能作为通用注入安全结论。
- 自动 marker 检查只是诊断辅助。空格变体、正确引用其他订单作为对照、解释恶意数字都可能触发误报，因此结论基于逐份人工阅读，未把 marker 命中率或模型核验当成客观正确率。
- 未修改 `.env`、已有用户、公共索引和任务前的 Embedding 客户端编辑。所有临时用户及来源资料均清理；结束后开发库仍为 1 个原有用户、0 个私人资料块、33 个公共资料块。

## 确定复现：工具摘要丢失证据

云舟文档分块实际为 270 字，集合时间 `16:47` 位于零基字符偏移 232，后面还有 `西门C3`、`紫鹭928`。完整检索与 Agent 实际检索都返回这些内容。随后：

```python
# app/services/local_tools.py:46
content = (it.get("content") or "")[:200].replace("\n", " ")
```

工具返回文本不含三项事实，模型回答“该资料不包含集合时间、入口或口令”。复测中单 Agent 还推测“文档未成功上传/未索引”或“写在图片中”，实际资料已成功上传且被检索到。这些故障原因没有证据支持。

多 Agent 的 `evidence_record()` 保存工具的返回文本，不会重新获取完整检索块。核验员无法看到已丢失的事实，于是将错误的否定回答判为 `passed`。公共 `search_knowledge` 在 `mcp_server/tools.py:132` 也使用相同 200 字裁剪；本次私人路径已实测，公共路径在代码层存在相同风险，未污染公共库构造对应样例。

建议后续修复：给模型保留完整的已选分块并附来源；上下文预算应作用于候选数量/整体长度，截断时明确标记；核验使用独立保存的完整检索证据。新增端到端回归应覆盖块尾事实，不能只测试 Top-K 命中或核验状态。本次仅诊断，没有修改生产检索与回答逻辑。

## 无关召回与外部模型降级

火星票价问题返回松岚活动、晨星 A/B、星河、青岚等 5 条资料，重排分数约为 `0.1243、0.0879、0.0754、0.0579、0.0499`。这些候选与问题无关；检索器目前按 Top-K 返回有限向量结果，没有最低相关度/可回答性门槛。这属于检索拒绝无关结果的边界，本次完整上下文问答正确拒答，没有观察到其诱发编造。不能直接选一个通用分数阈值，需要另行校准。

扩展诊断记录 7 次 Embedding、5 次 rerank 告警；复测记录 3 次 Embedding、1 次 rerank 告警。Embedding 降为本地 hash 伪向量，重排降为 RRF，因此不能把扩展诊断标为“全部采用真实模型且无降级”。云舟问题在两次测试的完整检索及实际 Agent 检索中都有全部正确事实；工具输出均丢失，所以截断根因不依赖某次向量/重排是否降级。首次 HTTP 基线 7 个案例无降级。

Embedding 上传故障还可能将伪向量写入与真实向量相同的业务表，后续查询恢复使用真实模型时存在表示空间混用风险。此次受影响的是已清理的临时合成语料，未重建/修改原有公共索引。
