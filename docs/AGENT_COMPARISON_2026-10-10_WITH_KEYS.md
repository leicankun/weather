## 主要变化

**数据源已生效，两种模式均受益。** 高德预检 HTTP 200、业务 `status=1 / infocode=10000`，Tavily 预检 HTTP 200 并返回 3 条来源。Agent 中 4 次 `web_search` 均返回标明 Tavily 的结果；旧对照中调用联网搜索没有得到结果。高德地铁、驾车查询在本轮实际执行，脱敏日志记录 50 次地理编码 HTTP 200、12 次驾车 HTTP 200、12 次公交 HTTP 200。日志观察数与独立预检分开记录，不作为完整服务商账单统计。

**路线从估算变成有 API 依据的线路。** 独立路线问题中，两种模式以前都拿到 3 套本地估算：地铁 / 公交约 57 分钟、7 元；本轮都拿到 6 套高德方案，包括 2 号线 → 广佛线 → 3 号线约 51 分钟、5 元，以及 7 号线 → 3 号线约 58 分钟、5 元。这里描述的是本次工具返回值，不承诺实际乘车耗时或当天票价永远如此。换乘线现在有工具依据，工具只保留部分线路 / 导航步骤，不等于完整导航。

**多 Agent 本轮能补充联网资料，但没有独有数据源。** 四领域问题中，多 Agent 使用两次联网搜索，在答案里增加检索摘要中的地铁运营时段，并推荐广东省博物馆；单 Agent 没调用联网搜索，也推荐了广东省博物馆和室内商圈。运营时段来自第三方网页摘要，未独立核对官方运营信息，不计为已确认的新事实。单 Agent 同样拥有 `web_search`，不能解释为单 Agent 无法获取这些资料；景点选择变化也不能单独归因于新增 Key。

**原来“多保留全天温度范围”的差异不稳定。** 原基线天气 + 穿搭 + 地铁两次中，单 Agent 未完整展示最低 / 最高温，多 Agent 展示了；本轮两次中，两种模式都展示 `21.6~31.2°C`。私人攻略的最终答案本轮也少了原先让用户确认上传是否成功的矛盾说明，但编排未修改，不能据此认定架构问题已修复。

## 仍然发现的问题

1. **驾车费用被当作打车费用。** 高德驾车工具在项目里仍按 `距离 × 0.5 元 + 过路费` 估算费用，没有读取出租车报价。路线问题的单 / 多回答都把约 9～17 元当成打车费用；单回答还自行添加“含起步价”。接入高德解决了路线数据来源，没有解决费用含义错误。
2. **日期没有贯穿专业工具和汇总。** 最后一组 `itinerary_route_outfit / 2` 中，行程节点已经给出明天“晴、21.6~32.6°C”；穿搭和路线节点把今天“阴、21.6~31.2°C”标为明天，天气节点没有调用工具，只问是否需要查询。汇总最终采用了错误的明天天气。单 Agent 此组采用了工具中的明天预报。
3. **联网搜索也会返回不适用的内容。** 四领域问题的天气搜索摘要含 9/30～10/4 的预报以及难以确认日期的页面；多 Agent 最终既报告天气工具的明天预报，又写“无法确认明天的具体天气”。重复天气复合问题还将实时“晴”和当天概况“阴”并列为两种描述，仍缺少时间粒度区分。
4. **外部失败会造成部分方案缺失。** 本轮记录 2 次“高德地理编码失败”警告，日志没有异常类型，因此不确定具体原因。单 Agent 追问用例只得到公交 / 地铁方案；多 Agent 最后一次行程路线问题只得到驾车方案。两次均没有整图失败，不能把 Key 已配置或 HTTP 200 等同于每次完整获取全部路线。
5. **任务条件仍有误读和多余调用。** 路线 Agent 在用户已写明广州南站时仍称没有出发地。单 Agent 在仅问“那我今天去那里怎么穿”的追问中额外调用路线工具；多 Agent 的攻略节点仍会搜索完整问题中的天气、交通内容，并没有只处理分配的景点子任务。
